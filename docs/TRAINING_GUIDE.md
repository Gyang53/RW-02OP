### 2.3 生成机器人 USD（MJCF → USD）

```bash
# 第一步：清理 MJCF（删掉斜板/参考体等非机器人元素）
python3 isaac/make_clean_mjcf.py
# 输出: assets/nezha/models/nezhav1/mjcf/nezha_isaac.xml

# 第二步：转 USD（需要 Isaac Sim 运行时，约 2 分钟）
cd /home/yangg/data/isaacsim/IsaacLab
env -u CONDA_PREFIX -u CONDA_DEFAULT_ENV \
  PYTHONEXE=$PWD/.venv/bin/python \
  ./_isaac_sim/python.sh \
  /home/yangg/data/model_sim/RW-02OP/RW-02OP_OpenWBipedController/isaac/convert_mjcf.py \
  --visualizer none
```

**为什么需要两步？** 原始 MJCF 里有三样东西不能带进 Isaac：
- `slope`（斜板）：会被当成机器人的一部分，导致物理爆炸
- `base_Estimate`：可视化参考体（自由关节），会干扰物理
- `floor`：Isaac Lab 自己管地面

### 2.4 Isaac Lab 训练环境的关键设置

训练命令必须通过 `_isaac_sim/python.sh` 启动（不能用裸 python 或 .venv）：

```bash
# 模板（记住这一行，后面所有 Isaac 命令都用它）
cd /home/yangg/data/isaacsim/IsaacLab
env -u CONDA_PREFIX -u CONDA_DEFAULT_ENV \
  PYTHONEXE=$PWD/.venv/bin/python \
  ./_isaac_sim/python.sh <你的脚本或命令>
```

> **为什么这么麻烦？** Isaac Sim 是"下载版"运行时（`_isaac_sim/`），它自带一套
> Python 环境。`.venv` 里装了 torch/rsl_rl 等训练库。用 `PYTHONEXE` 把两者桥接：
> 运行时环境 + 训练库。`env -u CONDA_PREFIX` 是为了防止 conda 的库冲突。

## 3. 快速验证：能不能跑

### 3.1 环境冒烟测试

```bash
cd /home/yangg/data/isaacsim/IsaacLab
env -u CONDA_PREFIX -u CONDA_DEFAULT_ENV \
  PYTHONEXE=$PWD/.venv/bin/python \
  ./_isaac_sim/python.sh \
  /home/yangg/data/model_sim/RW-02OP/RW-02OP_OpenWBipedController/isaac/smoke_env.py \
  --visualizer none --num_envs 4 --steps 50
```

**期望输出**：
```
[smoke] bodies (9): [base_link, abad_L_Link, ...]
[smoke] joints (8): [abad_L_Joint, hip_L_Joint, ...]
[smoke] action space: Box(-inf, inf, (4, 8), float32)
[smoke] obs space: Dict('policy': Box(-inf, inf, (4, 37), float32))
[smoke] step   0 base_z=0.880 rew=+0.015
[smoke] OK
```

看到 `OK` 就说明环境没问题。关注三个数字：
- **bodies (9)**：base_link + 4 条腿的 link
- **joints (8)**：abad/hip/knee/wheel × 左右
- **obs (4, 37)**：观测是 37 维（36 基础 + 1 高度指令）

### 3.2 冒烟不过？

| 报错 | 原因 | 解法 |
|---|---|---|
| `ImportError: No module named 'isaaclab'` | .venv 没激活 | 确认用了 `PYTHONEXE=.../.venv/bin/python` |
| `Failed to allocate on device 'cuda:0'` | 显存不足 | 关掉浏览器/IDE，或减 `--num_envs` |
| `cylinder-box collisions not implemented` | MJX 限制 | 用 mujoco_warp（本项目默认），不用 MJX |
| `nefc overflow` | 接触太多 | 在 `flat_env_cfg.py` 加大 `njmax`（当前 256） |

## 4. 训练你的第一个策略

### 4.1 基础训练（速度跟踪 + 高度 + 单边板）

```bash
cd /home/yangg/data/isaacsim/IsaacLab

env -u CONDA_PREFIX -u CONDA_DEFAULT_ENV \
  PYTHONEXE=$PWD/.venv/bin/python \
  ./_isaac_sim/python.sh \
  scripts/reinforcement_learning/train.py \
  --task Isaac-Velocity-Flat-Nezha \
  --rl_library rsl_rl \
  --num_envs 2048 \
  --visualizer none \
  --seed 1
```

**参数说明**：

| 参数 | 含义 | 建议值 |
|---|---|---|
| `--num_envs` | 并行环境数 | 2048（8GB 显存） / 4096（12GB+） |
| `--seed` | 随机种子 | 换种子=换一轮训练 |
| `--visualizer none` | 无界面训练 | 训练时不开窗口（省 GPU） |
| `--max_iterations` | 训练轮数 | 默认 1500，约 15 分钟 |

**训练输出**（每 50 iter 打印一次）：
```
Mean reward: 44.61
Episode_Reward/track_height: 0.6892
Metrics/base_velocity/error_vel_xy: 0.1036
Metrics/success_rate: 0.9792
Iteration time: 0.42s
Time elapsed: 0:02:43
ETA: 0:08:33
```

**怎么判断训练好了**：
| 指标 | 目标 | 含义 |
|---|---|---|
| `success_rate` | > 0.95 | 20 秒不摔的比例 |
| `error_vel_xy` | < 0.15 | 速度跟踪误差 (m/s) |
| `error_vel_yaw` | < 0.25 | 转向跟踪误差 (rad/s) |
| `track_height` | > 0.65 | 高度跟踪（1.0=完美） |
| `Mean reward` | > 40 | 总奖励（越高越好） |

**Checkpoint 保存在**：`IsaacLab/logs/rsl_rl/nezha_flat/<时间戳>/model_XXXX.pt`

### 4.2 训练耗时参考

| 显卡 | 环境数 | 吞吐 | 1500 iter 耗时 |
|---|---|---|---|
| RTX 5060 8GB | 2048 | ~48k steps/s | ~16 分钟 |
| RTX 4090 24GB | 4096 | ~100k+ steps/s | ~8 分钟 |
| CPU only | 64 | ~5k steps/s | ~2 小时（不推荐） |

## 6. Newton Viewer 键盘控制机器人

在 Newton Viewer 里直接回放策略并用键盘全功能驱动机器人——前进/后退/转向/蹲站/复位，
不用开 ROS2、不用三个终端，一个命令就是一个带键盘控制的图形窗口。
支持多环境并行（`--num_envs N`，键盘命令对所有环境生效）。

### 6.1 启动

```bash
cd /home/yangg/data/model_sim/RW-02OP/RW-02OP_OpenWBipedController

# 自动用最新的 checkpoint
./isaac/play_viewer_kb.sh

# 指定 checkpoint 和环境数：全能策略（行走+蹲站+起身）用 Full 任务训练的 ckpt
./isaac/play_viewer_kb.sh \
    /home/yangg/data/isaacsim/IsaacLab/logs/rsl_rl/nezha_flat/<run>/model_<n>.pt 4

# 16 个机器人一起走（看多样性/起身率）
./isaac/play_viewer_kb.sh <ckpt> 16

# Full 任务训练的 checkpoint 要配 Full 任务环境（TASK 环境变量，默认 Flat）：
TASK=Isaac-Velocity-Flat-Nezha-Full ./isaac/play_viewer_kb.sh <ckpt> 4
```

> **checkpoint 与任务要匹配**：37 维观测布局相同，不同任务的 checkpoint 物理上能加载，
> 但行为按训练分布走。Full 任务 checkpoint 用 `TASK=Isaac-Velocity-Flat-Nezha-Full`。
>
> **checkpoint 选择很关键**：`ls -t` 找到的"最新"不一定是走得最好的。
> 挑 checkpoint 先用 `isaac/eval_policy.py --visualizer none` 量化验证，再拿来 Viewer 回放。

### 6.2 键盘操作

**查看器窗口必须在前台**（点一下窗口标题栏）。首次启动约 2-3 分钟（加载 USD + mesh），
终端出现 `[kb] viewer 已绑定: NewtonViewerGL` 说明键盘通道接好了。
所有按键可叠加（如 W+D 前进右转、W+Z 边走边蹲）。

| 按键 | 功能 | 说明 |
|---|---|---|
| `W`（按住） | 前进（+1.0 m/s） | 释放即停 |
| `S`（按住） | 后退（−1.0 m/s） | |
| `A` / `D`（按住） | 左转 / 右转（±0.5 rad/s） | |
| `Z`（按住） | 蹲下（目标 0.45 m） | 高度以 0.25 m/s 缓动，松开保持 |
| `X`（按住） | 站高（目标 0.85 m） | |
| `C` | 回中间高度（0.70 m） | |
| `R` | 手动复位全部环境 | 演示"倒下→起身"循环：复位后全能策略会自己爬起来 |
| 关闭窗口 / Ctrl+C | 退出 | |

### 6.3 终端遥测

每 2 秒打印一行状态，不用盯窗口也能确认在动：

```
[kb] viewer 已绑定: NewtonViewerGL
[t=  2.0s] step=100 cmd=(+0.00,+0.00) vx=+0.03 z=0.720 h_cmd=0.70 fallen=0/4
[t=  2.0s] step=16300 cmd=(+1.00,+0.00) vx=+0.98 z=0.714 h_cmd=0.70 fallen=0/4
```

| 字段 | 含义 |
|---|---|
| `cmd=(vx, wz)` | 当前键盘指令 |
| `vx` | 机器人实际前进速度 (m/s)——与 cmd 前半接近 = 跟踪正常 |
| `z` | 1 号环境机身高度 (m) |
| `h_cmd` | 当前高度指令（Z/X/C 改变它） |
| `fallen` | 蹲得极低（z<0.35 m，多半是倒了）的环境数/总数 |

### 6.4 修改速度/转向/高度

编辑 `isaac/play_keyboard.py` 里 `KeyboardCommand.poll()`：

```python
if self._viewer.is_key_down(self._key_forward):
    fwd += 1.0        # 改这里：最大前进速度 (m/s)
if self._viewer.is_key_down(self._key_turn_left):
    turn -= 0.5       # 改这里：左转角速度 (rad/s)
if self._viewer.is_key_down(self._key_crouch):
    self.height[:, 0] = 0.45   # 改这里：蹲下目标高度
```

高度缓动速率在主循环里：`_rate = 0.25  # m/s`。

### 6.5 常见问题

| 现象 | 原因 | 解法 |
|---|---|---|
| 按键没反应 | 窗口不在前台 | 点一下 Newton Viewer 窗口再按 |
| 按键没反应、也没绑定日志 | viewer 还没创建完 | 等出现 `[kb] viewer 已绑定`（最多 3 分钟） |
| 机器人抖动、不走 | checkpoint 不会走路（训练退化） | 换已验证 checkpoint，用 eval_policy 先验证 |
| 蹲下后站不起来 | checkpoint 没练过起身/低高度 | 用 Full 任务训练的 checkpoint |
| 机器人每 10 s 蹲一下 | 高度指令被随机重采样 | 正常情况不会发生（脚本已接管高度指令） |
| 窗口黑的 | 首次初始化慢 | 等 2-3 分钟 |
| OOM | 显存不足 | 减小第二个参数（环境数），或关浏览器 |

### 6.6 与第 7 章（MuJoCo 键盘）的区别

| | 本章（play_viewer_kb.sh） | 第 7 章（policy_node + sim_node） |
|---|---|---|
| 物理引擎 | Newton（GPU） | MuJoCo（CPU） |
| 终端数 | 1 个 | 3 个 |
| 用途 | 训练效果快速回放 | 部署链路验证（与实机同构） |
| 键盘 | W/S/A/D + Z/X/C + R | W/A/S/D + Z/X 蹲站 |
| 多机器人 | 支持（`--num_envs`） | 单台 |
| 起身演示 | R 复位后自动起身（Full ckpt） | 无 |

## 6A. 训练"全能"策略（行走+蹲站+起身，多环境并行）

第 4 章的 Flat 任务和第 8 章的 GetUp 任务各管一头：Flat 会走会蹲但倒了起不来，
GetUp 会起身但行走/高度精度退化（实测 vx 误差 0.068 → 0.42 m/s）。
`Isaac-Velocity-Flat-Nezha-Full` 任务把两者合并成一个策略：

### 6A.1 任务定义

`source/isaaclab_tasks/.../nezha/full_env_cfg.py`（在 Flat 基础上）：

| 项 | 值 | 说明 |
|---|---|---|
| `reset_fallen` | 概率 0→0.35，8000 步升温 | 一部分回合从倒地开始，比 GetUp 更慢更温和 |
| `nan_state` 终止 | 启用 | 数值发散直接判死，防 NaN 污染梯度 |
| 动作限幅 | ±3.0 | 倒地时防接触求解发散 |
| `base_contact` 终止 | 关闭 | 倒地时 base_link 本来就贴地 |
| `track_height` | weight 1.5 / std 0.20 | 站立精度与起身梯度折中 |
| 高度指令范围 | 0.45–0.85 | 全范围蹲站 |
| 回合 | 20 s | 与 Flat 相同 |

### 6A.2 训练（resume 自 Flat 好模型）

```bash
cd /home/yangg/data/isaacsim/IsaacLab
export RUN="env -u CONDA_PREFIX -u CONDA_DEFAULT_ENV PYTHONEXE=$PWD/.venv/bin/python ./_isaac_sim/python.sh"

# 从会走的 checkpoint 出发，3000 iters（约 25 分钟，RTX 5060）
$RUN scripts/reinforcement_learning/train.py \
    --task Isaac-Velocity-Flat-Nezha-Full --rl_library rsl_rl \
    --num_envs 2048 --visualizer none --seed 0 --max_iterations 3000 \
    --checkpoint logs/rsl_rl/nezha_flat/<flat_run>/model_<n>.pt
```

多开机器人训练就是 `--num_envs`：2048 个环境并行采样（GPU 吞吐 ~48k steps/s），
想更稳就加 envs 或 iters。checkpoint 存在 `logs/rsl_rl/nezha_flat/<新 run>/model_<n>.pt`。

### 6A.3 评测三件套

```bash
CKPT=logs/rsl_rl/nezha_flat/<run>/model_<n>.pt

# 行走+高度（Flat 任务；Full 训练的 ckpt 在 Flat 上评即可看行走精度）
$RUN <ws>/isaac/eval_policy.py --visualizer none --num_envs 32 --steps 800 --checkpoint $CKPT

# 起身（Full 任务 + 1500 步 ≈ 12.5 s；起身需要 >10 s，评短了全是 0%）
$RUN <ws>/isaac/eval_getup.py --task Isaac-Velocity-Flat-Nezha-Full \
    --visualizer none --num_envs 64 --steps 1500 --fall_prob 0.6 --checkpoint $CKPT
```

| 指标 | 合格线 |
|---|---|
| `mean \|vx - cmd\|` | < 0.15 m/s |

### 6B.1 现象与量化

用户主观描述："张腿走路、像跪地爬，不是靠轮子"。用 `isaac/diag_locomotion.py` 量化后：

| 双轮同时接地 | **98.5%** | 0.2% |

### 6B.2 根因（按发现顺序）

1. **`wheel_vel.clip = ±3.0` 的单位错误（决定性根因）**
   `JointVelocityActionCfg.clip` 作用在**缩放后的目标**上，即 rad/s。
   ±3.0 把轮速上限锁在 3 rad/s = **0.38 m/s**，而速度指令可到 1.0 m/s。
   策略要达标只能让腿蹬地辅助 → 学会了"张腿 + 腿划水"。
   改为 `±60 rad/s` 后，同一个策略立刻恢复 98.0% 双轮接地、vx 0.80。
2. **倒地/起身样本与行走混在同一批环境**
   每回合按 50% 概率倒地 → 起身动作与行走动作在同一批梯度里竞争，
   叠加"倒地回合不做基座接触终止"，策略发现腿式推进在两个分布上都够用。
3. **按高度阈值判定"跪地"**（`z ∈ [0.30,0.45]` 就罚）把合法的低趴蹲行也罚了，
   等于把策略往"抬腿抬身"推。必须用接触传感器判定：基座接触 **且** 两轮都未接触。
4. **`env_origins` 未叠加**：`default_root_state` 是环境局部坐标，直接写 sim 会把
   倒地机器人瞬移到世界原点（多环境叠在一起互相踩踏）。
5. **障碍物与环境格重叠**：默认 env_spacing 2.5 m，1.6 m 宽障碍摆在 +2.5 m 会压住邻居。

### ⚠ 更正上一版文档的一个错误数据

上一版写的“饱和力矩下轮底离地 0.68~1.05 m”是**测量 bug**：用 `wheel_body_z - 0.127`
估算轮底，而轮 link 原点和轮心不重合，算出来的离地高度虚高。

用碰撞圆柱支撑点重算（`scripts` 里可复现）：MuJoCo 侧同参数下 base_z 峰值 1.144 m、
轮底 1.082 m；但**同一个原语在 Isaac（策略实际运行的引擎）里 base_z 峰值只有 0.604 m**。
两个引擎/接触参数下差异巨大，未定位；以 Isaac 为准：**当前配置下原语产生不了可用的起跳**。

### 执行器 vs 几何：A/B 判定（关键结论）

同一条跳跃原语、同一 S06 几何、同一个 0.18 m 障碍，**只改腿执行器**：

| 腿执行器 | base_z 峰值 | 弹道阶段 | 前进距离 | 结论 |
|---|---|---|---|---|
| stiffness 40 / effort 120（现状） | 0.604 m | 无 | 0.09 m | 跳不起来 |
| **stiffness 150 / effort 250** | **1.180 m** | 有（抬升 0.58 m） | ≈0 m | **能起跳，但原地弹跳** |

任务：`Isaac-Velocity-Flat-Nezha-S06-JumpTestStrong`（`jump_test_strong_env_cfg.py`，
只覆盖 `scene.robot.actuators["legs"]` 的 stiffness/damping/effort，几何与模型完全不动）。

**结论**：
1. 起身/跳跃跳不起来的**硬瓶颈是腿部执行器**（40 N·m/rad 的隐式 PD 无法在 0.16 s 内
   把 20 kg 机身送出站高），不是 S06 的腿长。
2. 加强执行器后能起跳，但**缺乏水平速度**——原语在蓄力/弹射相位锁轮是对的（否则反作用力
   变成前进），但 `tuck` 相位只恢复 0.22 s 的轮速，腾空期间前进不足，落在障碍上/原地。
   下一步要在**起跳前就带速度**（不锁轮、改用轮速前馈补偿）或延长 `tuck` 的驱动时间。

### ⚠ 实机力矩上限：仿真 120 N·m 已超真机 90 N·m

`src/nezha_lqr_controller/config/wb_motor_config.json`：

```
motor_params: max_current = 60 A, kt = 2.1 N·m/A  →  max_torque = 90 N·m（全部 8 个电机相同）
```

| 项 | 数值 |
|---|---|
| 实机峰值力矩 | **90 N·m** |
| 当前仿真 `effort_limit_sim` | 120 N·m（**已超真机 33%**） |
| “强执行器”对照实验 | 250 N·m（**2.8 倍于真机，不可实现**） |

**因此：把执行器提到 250 N·m 让仿真跳起来是没有意义的**——真机做不到，属于 sim-to-real 造假。
跳跃/起身的可行路线必须落在 ≤90 N·m 内。

进一步分析：力矩并非能量上的瓶颈——90 N·m 覆盖膝行程 2.12 rad，两腿合计做功 ≈380 J，
抬升 20 kg 理论可到 1.9 m。真正的疑点是**腿在离地前就撞上关节限位**（实测膝角冲到
+1.14 rad，而限位是 +0.663），Isaac 的限位约束把冲量吸收掉了（base_z 只到 0.604），
而 MuJoCo 的限位更硬（base_z 到 1.144）。这才是引擎差异的来源，不是扭矩不够。

下一步（都 ≤90 N·m，不改真机）：
1. 伸展目标设在限位前（+0.60 rad）并提前 20 ms 撤力矩，让离地发生在“腿接近全伸”时，
   而不是撞限位；用 MuJoCo/Isaac 对比验证限位模型差异。
2. 把 `effort_limit_sim` 改回 **90**（与真机一致），重训行走/起身/跳跃——否则策略会学到
   真机做不到的动作。
3. 若仍不足，再考虑恢复部分腿长（×0.75），它同时改善起身与跳跃，且不违反力矩约束。

### 90 N·m 下的跳跃上限实测（第 2、1 步都已完成）

**第 2 步：仿真力矩对齐真机 90 N·m 并重训基线**（`nezha_s06_cfg.py` effort 120→90）

| 指标 | 120 N·m（旧） | **90 N·m（对齐真机）** |
|---|---|---|
| 双轮接地 | 98.3% | **98.0%** |
| vx（指令 1.0） | 0.781 | **0.928** |
| vx 误差 | 0.143 | **0.081** |
| 腿速 / abad | 0.29 / ≈0 | 0.38–0.66 / −0.09 |
| 训练成功率 | 0.89 | 0.93 |

结论：**降力矩到真机水平后轮式行走不受损**（甚至更准）。checkpoint `2026-11-11_14-33-09/model_8748.pt`。

**第 1 步：限位感知的伸展时序**（0.18 m 障碍，effort 固定 90）

| 控制策略 | base_z 峰值 | 抬升 | 腾空帧占比 |
|---|---|---|---|
| 饱和目标 +2.0 rad（撞限位） | 0.604 | +0.00 | 40% |
| 目标 +0.663（限位前）+ kp 150 | 0.609 | +0.01 | 40% |
| 目标 +0.663 + **kp 400** | **0.704** | **+0.10** | 74% |
| 目标 +0.663 + **kp 1000** | 0.722 | +0.12 | 77% |
| 恒定力矩仿真（状态反馈超前量） | 0.678 | +0.08 | 78% |

**结论（可交付的能力边界）**：
- 90 N·m + ×0.6 腿长下，**最大抬升 ≈ 0.10–0.12 m**，与控制器策略无关（三种实现都撞到同一上限）。
- 因此**可越障碍高度 ≤ 0.12 m**；0.18 m 需要约 1.5–2 倍的竖直能量，即 ~200 N·m（真机没有）
  或更长的腿。
- kp 从 40 提到 400 是关键改善（+0.10 m）：固定目标下 PD 在接近目标时自动刹车，
  高刚度让力矩在整个行程维持在上限附近。

**0.12 m 障碍的闭环验证（A/B，ktorque 400）**：机器人能接近并起跳（base_z 0.750 = +0.15 m，
为目前最高），但**两组都没有越过**——两者最终都被推回起始位置（dx ≈ 1.2 m）。
注意本任务已关掉 `obstacle_cleared` 奖励，障碍物不会被重摆，所以 dx 稳定在 1.2 m 就是
"回到起点、未越过"的确凿证据。

**因此真正的短板已不是高度，而是水平速度**：原语在蓄力/弹射相位把轮子锁到 0 速度，
竖直弹射有了，但没有向前的速度分量，落地就撞回障碍。下一步应改为
"保留部分前进速度"（例如蓄力期维持 -4 rad/s、弹射期给 -8 rad/s 的正向轮速），
让竖直弹射与水平运动合成抛物线越过障碍；高度上限（+0.12~0.15 m）已经够用。

**轮速前馈实验结果**（蓄力 −4 rad/s、弹射 −8 rad/s、腾空 −10 rad/s）：
base_z 0.714、最近距离 0.78 m、最终 dx 仍 ≈1.2 m，**依旧未越过**。

结合全程数据，越障失败的机制已经清楚：
1. 竖直弹射成立（+0.10~0.15 m），但机器人在 8 s 内只前进 0.42 m —— 起跳→落地→被推回，
   形成"顶在障碍前反复弹跳"的循环；
2. **触发时机没有和飞行时间匹配**。正确的关系是：在距障碍 `d ≈ vx × T_flight`
   处起跳，其中 `T_flight ≈ 2·vz/g`（vz≈1.0 m/s → T≈0.2 s，vx=1.0 → d≈0.2 m）。
   当前用固定 0.9 m 触发，起跳点离障碍太远，落地在障碍之前，随后被顶住。

**下一步（唯一剩下的、明确的控制问题）**：把触发做成闭环——
起跳距离 = `vx × 2·vz/g`，并用一次飞行后是否越过做在线校准。
这不是训练问题，也不需要改模型；属于原语的控制器设计。

**闭环触发实验（d = vx·(蹲下 + 2·vz/g)）**：base_z 0.705，仍未越过。
同时暴露一个更基础的问题：**在 JumpTest 环境里机器人几乎不前进**
（8 s 平均前进 0.14 m、逐环境 0.0~0.79 m），而同一策略在 `eval_skills` 的 S06 任务里
跑 0.93 m/s。说明这是**测试环境自身的问题**，不是原语或策略的问题——
在机器人无法正常行驶的环境里，任何"越障成功率"都没有意义。

**当前可信结论（不做过度声称）**：
- 90 N·m 下轮式行走：已验证（双轮接地 98.0%、vx 0.928、误差 0.081）。
- 90 N·m 下竖直起跳：已验证（base_z 0.60→0.70~0.75，抬升 0.10~0.15 m）。
- 越障：**未验证**。JumpTest 环境存在"机器人不前进"的缺陷，需先修该环境
  （对比 S06 与 JumpTest 的差异：障碍物碰撞组、初始位姿固定方式、hcmd=0.50 与 0.60 等），
  再用同一 A/B 计量。

**排查 JumpTest 不前进的建议顺序**：
1. 在同一 JumpTest 环境里把障碍物停到 100 m 外，看是否恢复正常行驶 → 若是，问题在障碍物
   碰撞/摆放（例如 1.2 m 宽障碍横跨了多个环境格）。
2. 把 `hcmd` 从 0.50 改回 0.60，排除高度指令与训练分布的差异。
3. 检查 `reset_base` 的 pose_range 置零是否把 z 也清零（应保持 0.602）。

### 🔑 纠正：此前所有 hw90 越障读数都是"刚度作用域"错误造成的假象

`jump_test_hw90_env_cfg.py` 最初把 `legs.stiffness` **全局**设为 400，
而策略是在 stiffness=40 下训练的 → **步态被破坏**。决定性证据：把障碍物停到 100 m 外，
机器人 8 s 仍只前进 0.34 m（正常应 ~7 m），且 base_z 在 0.119~0.756 之间乱跳。

修复方式（已实现于 `jump_primitive_test.py`）：**按环境、按相位写刚度**
```python
robot.write_joint_stiffness_to_sim_index(
    stiffness=torch.where(prim.active.unsqueeze(-1), 400.0, 40.0), joint_ids=leg_ids)
```
即正常行走保持训练值 40，**只有正在执行跳跃原语的环境**用 400。

修复后实测（0.12 m 障碍，effort 90，16 envs × 400 步）：

| 指标 | 全局 kp400（错误） | **按环境 kp（正确）** |
|---|---|---|
| 平均前进 | 0.14 m | **0.80 m** |
| 实测越过障碍 | 0（被障碍挡住） | **1 个环境明确越过**（dx = −2.14 m，即越过 2.14 m） |
| base_z 峰值 | 0.705 | 0.709 |

**结论**：
- 越障机制**已被证实可行**（有环境实际越过了 0.12 m 障碍），但**可靠性低（≈1/16）**；
- 可靠性低的原因是原语触发与步态的耦合——机器人仍只前进 0.80 m/8 s（正常约 7 m），
  说明频繁触发原语打断了正常行驶，需要"只在必要时触发 + 触发后不反复触发"的调度器；
- 之前的"0% 越障"结论作废，属测量/作用域错误。

**触发调度器实验**（冷却 1.5 s + 要求障碍在前方 + vx > 0.3）：
平均前进 0.62 m、base_z 0.633、全部环境停在障碍前 0.39~0.78 m，**无环境越过**。
比上一轮（1/16 越过）更差，说明冷却反而减少了成功机会——真正的约束是
**机器人在该环境里始终无法持续行驶**（8 s 只走 0.62~0.80 m，正常约 7 m）。

至此可以确定：越障这条线上的阻塞点已经不在"跳跃能力"，而在
**JumpTest 环境本身无法复现 S06 的正常行驶**。在修好这一点之前，
继续调触发/时序/刚度都不会有可靠结论。

**建议的收尾方式（按投入产出）**：
1. 先修 JumpTest 行驶问题：直接在 `eval_skills` 能正常跑的前提下，用它的
   `park_obstacle_far` 机制做对照——即复用已验证可行驶的环境，只额外注入障碍物，
   而不是新建一个独立任务。
2. 行驶恢复后，用 `--fixed_trigger` 扫 0.3/0.5/0.9 m 三个触发距离，取越过率最高的。
3. 越障闭环稳定后，再把该原语接进 `play_keyboard.py`（已有 `--jump` 开关）做人工验证。

### 6B.5e 孤立诊断的有效性修正：极端蹲姿在动力学上不稳定

给 `diag_leg_extension.py` 加了**前置断言**（`projected_gravity_z` 必须 < −0.8，否则中止），
立刻暴露了此前所有该诊断的测量都是无效的：

| 尝试 | 姿态设置方式 | 稳定后 g_z | 结论 |
|---|---|---|---|
| 瞬移到 z=0.34 + 折叠关节 | teleport | **+0.16**（≈水平=躺倒） | 测量作废 |
| 从 standing 用 PD 驱动到 knee −1.40 / hip +0.99 | PD | **−0.32**（倾斜约 70°） | 测量作废 |

**根因**：FK 表给出的"竖直蹲姿"（knee −1.40 → hip **+0.99**）**在动力学上不成立**——
髋角打到 +0.99 时机身被顶翻，机器人倒下而不是蹲下。也就是说：

> FK 求出的"腿竖直"配置 ≠ 机器人能稳定站住的配置。
> 机器人真实的稳定姿态是**腿带倾角**的（策略实测：knee ≈ −0.92、hip ≈ +0.40、z ≈ 0.47）。

**对跳跃/起身的含义**：
- 可用蓄力下限不是 FK 的 0.364 m，而是**稳定蹲姿 ≈0.37 m**；
- 从该姿态伸展时，髋只需从 +0.40 走到 −0.25（0.65 rad，幅度温和），是可行的；
- 但机身会在伸展中被顶得抬头/后仰，这正是有效率只有 0.37 的可能原因（能量转成姿态变化）。

**下一步（正确的诊断设计）**：以「policy 稳定蹲姿」为起点（不瞬移、不用 FK 极端角），
用 PD 伸展并同时记录 `projected_gravity_z`，把"抬升"和"姿态变化"分开统计。

### 6B.5f 有效测量（姿态全程竖直）: 稳定姿态下膝伸展**不产生向上速度**

按"从策略稳定蹲姿出发 + 全程校验姿态"的正确设计重跑（`diag_leg_extension.py`）：

| 阶段 | z | g_z（−1=竖直） | 轮接地 |
|---|---|---|---|
| 站立 | 0.552 | −0.90 | 1.00 |
| 蹲姿（knee −0.92 / hip +0.40） | 0.513 | −0.85 | 0.88 |
| 伸展（knee→+0.66, hip→−0.25） | 0.42–0.55 波动 | −0.59 … −0.86 | 0.50–1.00 |

**结果**：
- 抬升仅 **+0.032 m**，**竖直速度全程为负**（峰值 −0.289 m/s，即一直在下落）
- 姿态变化 0.27（g_z 摆幅），轮子在第 21 步失去接地
- 判定：**在可稳定站立的姿态下，膝伸展无法把机身向上推**——能量转成下落与姿态摆动。

**这是目前最可信的结论**（前几次诊断都是塌姿读数，已作废）。它一次性解释了：
- 跳跃实测只能到 +0.10~0.15 m（且那次是从更不稳定姿态得来的）
- 起身 0%：起身同样依赖"腿蹬地把机身顶起"，而这条力传递链在稳定姿态下几乎为零

**伸展速度扫掠（`--sweep`）暂不可用**：本脚本的前置断言在扫掠前执行，
而环境复位带随机化（站立 z 在 0.50~0.55 之间波动、蹲姿 g_z −0.71~−0.85），
导致断言时好时坏并中止。要做扫掠必须先**固定随机种子 / 关闭复位随机化**
（`reset_base` 的 pose_range 置零、`reset_robot_joints` 关闭扰动量），
让每个 ramp_steps 从完全相同的初态出发。这一项还没做。

**可选的后续（成本递增）**：
1. 伸展时**主动下压轮子**（轮速前馈 + 轮扭矩）产生额外地面反力，而非只依赖腿；
2. 加长腿（行程↑）——但需重做模型并重训；
3. 换越障策略：不做垂直跳，用轮扭矩冲坡/顶越（实测 ≤0.12 m 可滚过）。

### 但"静态姿态指令"无法复现这些姿态（最后一次诊断结论）

把上表当作静态指令逐步下发（沙发式 keyframe），实测姿态会漂移：

**"抬升"其实是机体倾斜导致 base 原点抬高，不是真正的竖直弹射。**

**结论**：机器人靠的是**动态平衡**（轮子持续驱动 + 姿态闭环），
静态 keyframe 序列无法复现。要跳跃/起身，必须：
1. 用 RL 学（此前 4000 iters 未成功，属于探索难点），或
2. 用参考动作模仿（录下策略自身成功执行某动作的轨迹作为 reference），或
3. 加长腿（改变物理上限）。

### 参考轨迹回放：竖直速度上限 ≈1.1–1.2 m/s（定量结论）

`isaac/diag_replay.py`：先用策略把 h 指令 0.35→0.60 的**动力学有效轨迹录下来**
（z 0.373 → 0.599，120 步，g_z 全程 ≈−1.00），再按 1×/2×/3×/4× 速度把它当位置目标回放：

| 倍速 | z_end | z_max | vz_end | **vz_max** |
|---|---|---|---|---|
| 1× | 0.526 | 0.607 | −0.364 | **+1.185** |
| 2× | 0.510 | 0.592 | −0.579 | **+1.098** |
| 3× | 0.526 | 0.552 | −0.573 | **+1.038** |
| 4× | 0.343 | 0.550 | −1.212 | **+1.099** |

**关键结论**：
1. 这是目前测到的**最高竖直速度 ≈1.1–1.2 m/s**（比之前静态 keyframe 的 0.3–0.5 高得多，
   因为这条轨迹来自策略的动力学有效动作，不是硬编码姿态）。
2. 对应弹道高度 = v²/(2g) ≈ **0.06–0.07 m**；加轮半径 0.127 m，**可越障碍 ≈0.10–0.12 m**。
3. **压缩时间没有帮助**（1×~4× 的 vz_max 基本一致，1× 最高），说明限制不在"伸展速度"，
   而在系统的能量/推力上限。
4. 所有档位结束时 vz 为负（回落后塌下），说明**没有闭环姿态控制就无法维持站立**——
   这也是起身 0% 的同一原因。

**要越 0.18 m 障碍需要 vz ≈ 1.9 m/s**（当前 1.2 的 1.6 倍，能量 2.5 倍）。
在 ×0.6 腿长 + 90 N·m 力矩下不可达；只有加长腿或换机械方案能改变这个上限。

### ❗ 最终裁定：机器人没有弹道阶段（base_z 从未超过站立高度）

把跳跃原语改成**回放策略实测参考轨迹**（`vertical_ref.json`，120 帧，1× = 2.4 s，
轮速为 0，完全复刻 `diag_replay` 的录制条件）后，在 `JumpTest`（0.12 m 障碍）实测：

| 指标 | 结果 |
|---|---|
| 触发原语 | 15/16 环境 |
| **base_z 峰值** | **0.605 m**（站立 0.60）→ **没有弹道阶段** |
| 双轮离地帧占比 | 28.0% |
| 越过 0.12 m 障碍 | 13/16（`dx` 出现 −0.41/−0.36，即越过了约 0.4 m） |

**结论（与前几轮所有"抬升"数字的关系）**：
- `base_z` 在所有配置、所有时序下都**没有超过 0.61 m**，即**从未出现真正的腾空**；
- 之前报过的 "+0.10~0.15 m 抬升"来自**姿态倾斜把 base 原点抬高**（同一时期 g_z 从 −1.0 漂到 −0.6），
  不是竖直弹射——这次以 base_z 与 g_z 同测，口径统一后不再成立；
- 0.12 m 障碍能过，是**靠轮半径 0.127 m 滚/顶过去**，不是跳过去的。

**因此当前硬件/几何下的能力边界（最终）**：
- 可越障碍 ≈ **0.12 m**（滚过，无需腾空）
- 跳跃腾空：**0**（无力矩/行程产生弹道）
- 倒地起身：**0%**

要真正获得跳跃能力，必须改物理条件（加长腿→增加行程，或提高电机力矩），
这不是软件/训练能补的。

### 6B.8 跳跃：物理可行性已验证，端到端未闭环

**MuJoCo 实测**（`isaac/jump_primitive_check.py`，S06 模型 + 0.15 m 台阶）：

| 方式 | 结果 |
|---|---|
| PD 跟踪「蹲 → 伸」轨迹 | ❌ 只回到站高（base_z 0.602→0.603，轮离地 3 cm）——目标一到扭矩就撤 |
| **膝力矩饱和 +120 N·m（0.16 s）** | ✅ vz 2.92 m/s、base_z 0.741、**轮底离地 0.68 m** |
| 叠加髋 +60 N·m 助推 | ✅ vz 4.85 m/s、base_z 1.175、**轮底离地 1.05 m** |

结论：0.15 m 障碍在物理上可跳，**必须用力矩饱和**；这也解释了纯 RL 为什么学不到
（它一直在搜索小幅位置动作，没找到饱和扭矩路径）。

**Isaac 管线内实测**（`isaac/jump_primitive_test.py`，把原语动作注入策略环境）：
- base_z 峰值 0.82–0.85 m（站立 0.60）→ 原语在真实训练管线里确实弹射
- 16/16 环境出现双轮离地
- 越障计数 0%：**计量受障碍物自动重摆干扰未闭环**（越障后 `obstacle_cleared_reward`
  会把障碍物重摆到前方 1.2 m，`x > ox` 判定随之失效；同一日志里 obs_dx 从 1.2 跳到
  1.43 说明确实越过了，但位移均值与之一致性未对上，按未验证处理）

**已修正（按 Isaac 实测标定）**：
1. 轮子正转对应世界 −x → `WHEEL_ACTION = -1.0`（-10 rad/s ≈ 前进 1.27 m/s）。
2. 原语改为从骑行姿态出发（`HIP_RIDE=+0.40`、`KNEE_RIDE=-0.92`），三个相位都显式给髋目标，
   避免策略在该窗口输出冲突髋角。

**仍未闭环的观察**：V4 场景障碍高度课程从 0.04 m 起，实测机器人**直接滚过/顶过去**，
不需要跳（player 遥测里 `obs_dx` 每约 1 s 从 1.2 跳回 1.2，说明持续越障）。
因此"必须跳跃才能通过"的场景还没有验证——需要把障碍固定在 ≥0.20 m（轮半径 0.127 m
的两倍）才能形成真正需要腾空的台阶。
2. 站立姿态（knee=0、base_z 0.602）时膝/髋碰撞体可能拖地（真实骑行姿态是
   knee≈−0.92、base_z≈0.47），原语应从骑行姿态出发，蓄力行程只剩约 0.48 rad，
   弹射能量需重新标定。


## 8. 调优指南：策略不好怎么办

### 8.1 训练不收敛（success_rate 上不去）

**先看是哪种不好**：

| 症状 | 可能原因 | 解法 |
|---|---|---|
| 一开始就不动 | 探索噪声太大 | 降低 `init_std`（在 `agents/rsl_rl_ppo_cfg.py`） |
| 前期能走后面倒 | 奖励权重不平衡 | 加大 `track_lin_vel` 或减小 `dof_torques` |
| 一直小幅抖动 | PD 增益太高 | 在 `nezha_cfg.py` 降 `stiffness` |
| 摔倒率高 | 终止太严格 | 放宽 `min_base_z` 或 `max_tilt_cos` |
| reward 剧烈震荡 | 学习率太大 | `--lr 5e-5` |

### 8.2 奖励权重速查

在 `nezha/flat_env_cfg.py` 里调（改完重训）：

```python
self.rewards.track_lin_vel_xy_exp.weight = 1.5    # 前进速度跟踪（主要目标）
self.rewards.track_ang_vel_z_exp.weight = 0.75     # 转向跟踪
self.rewards.track_height.weight = 1.5             # 高度跟踪
self.rewards.track_height.params["std"] = 0.45     # 高度容差（σ，越大越宽松）
self.rewards.flat_orientation_l2.weight = -2.5     # 机身水平惩罚（防侧翻）
self.rewards.dof_torques_l2.weight = -2e-4         # 力矩惩罚（越小动作越柔和）
self.rewards.action_rate_l2.weight = -0.01         # 动作变化率惩罚（防抖动）
self.rewards.lin_vel_z_l2.weight = -2.0            # 垂直速度惩罚（防弹跳）
```

**调参口诀**：
- 不前进 → 加大 `track_lin_vel`，减小 `torques`
- 抖动大 → 加大 `action_rate` 惩罚，减小 `dof_acc`
- 侧翻 → 加大 `flat_orientation` 惩罚
- 高度不跟 → 加大 `track_height`，减小 `std`

### 8.3 物理参数调优

在 `nezha_cfg.py`（机器人配置）里调：

```python
"legs": ImplicitActuatorCfg(
    joint_names_expr=[LEG_JOINTS],
    effort_limit_sim=120.0,     # 最大力矩 (N·m)
    velocity_limit_sim=30.0,    # 最大角速度 (rad/s)
    stiffness=40.0,             # PD 位置增益 kp
    damping=2.0,                # PD 速度增益 kd
),
"wheels": ImplicitActuatorCfg(
    joint_names_expr=[WHEEL_JOINTS],
    effort_limit_sim=40.0,
    velocity_limit_sim=50.0,
    stiffness=0.0,              # 轮子不做位置控制
    damping=2.0,                # 轮子速度增益
),
```

| 参数 | 效果 | 注意 |
|---|---|---|
| `stiffness` ↑ | 腿更硬，响应快 | 太高会震荡 |
| `damping` ↑ | 更稳定，但响应慢 | 轮子的 damping = 速度控制增益 |
| `effort_limit` ↑ | 力气大 | 太大会物理发散 |

### 8.4 训练技巧（从实践中总结的）

1. **热启动**：用已有 checkpoint 继续训练新能力，比从零快 3~5 倍
   ```bash
   --checkpoint logs/rsl_rl/nezha_flat/<旧run>/model_XXXX.pt
   ```

2. **降低学习率微调**：热启动时用 `--lr 1e-4`（默认 3e-4），避免破坏已有能力

3. **换种子重跑**：RL 有随机性，同一配置不同种子结果差很多。跑 3 个种子取最好的

4. **保存频率**：默认每 50 iter 存一次。想多留几个中间结果改 `save_interval`

5. **早停**：看到 `success_rate` 连续 200 iter 不涨就可以停了（Ctrl+C，checkpoint 已保存）

### 8.5 sim-to-deploy 的高度观测差异（已修复，记录坑）

**Isaac 训练时**：`height_commands` 观测 = `UniformHeightCommand.command`
= **绝对高度**（0.45~0.85 m，`mdp.generated_commands` 直接返回）

**部署节点旧版本**：`height_cmd_norm = (h - 0.65) / 0.25`（错误地做了归一化）
→ 策略收到的值在 [-0.8, +0.8]，而训练时是 [0.45, 0.85]，维度对但数值完全不同

**修复**：`isaac/policy_node_isaac.py` 已改为 `np.array([self.height])`（绝对高度）。
如果策略跑起来姿态不对、蹲不下去/站不起来，先检查这里的观测格式。

### 8.6 起身训练的特殊配置

起身是特殊任务，用 `Isaac-Velocity-Flat-Nezha-GetUp`（不是普通任务）：

```bash
env -u CONDA_PREFIX -u CONDA_DEFAULT_ENV \
  PYTHONEXE=$PWD/.venv/bin/python \
  ./_isaac_sim/python.sh \
  scripts/reinforcement_learning/train.py \
  --task Isaac-Velocity-Flat-Nezha-GetUp \
  --rl_library rsl_rl \
  --num_envs 2048 \
  --visualizer none \
  --checkpoint logs/rsl_rl/nezha_flat/<速度策略run>/model_XXXX.pt   # 热启动
```

**起身任务的关键差异**：
- 50% 回合从倒地姿态开始（`reset_to_fallen` 事件）
- 倒地姿态：`abad=-0.32`（腿朝地面张开）+ `knee=0.663`（伸直）
  → 这个姿态让轮子穿入地面，给策略一个可用的支撑点
- 不检查 `base_contact`（倒地时 base_link 本来就贴地）
- 动作限幅 ±3.0（防止倒地时输出极端值导致数值发散）
- `track_height` 用 σ=0.45（起身过程中高度误差很大，需要宽梯度）

   ```python
   self.rewards.slope_bonus = RewTerm(

   )
   ```

   ```python
   # 在 nezha/__init__.py 里

   ```


### 9.3 加新的观测维度

观测顺序（37 维）在 `flat_env_cfg.py` 的 `ObservationsCfg` 里定义：

```python
class PolicyCfg(ObsGroup):
    base_lin_vel = ObsTerm(func=mdp.base_lin_vel, ...)       # 0:3
    base_ang_vel = ObsTerm(func=mdp.base_ang_vel, ...)       # 3:6
    projected_gravity = ObsTerm(...)                          # 6:9
    velocity_commands = ObsTerm(...)                          # 9:12
    joint_pos = ObsTerm(func=mdp.joint_pos_rel, ...)          # 12:20
```

3. 输出：实机电机指令
4. 注意 sim-to-real gap：训练时的 PD 增益/摩擦系数要和实机标定一致

## 10. 常见问题排查

### Q: 训练时 GPU OOM
```
RuntimeError: Failed to allocate XXX bytes on device 'cuda:0'
```
**解法**：减 `--num_envs`（2048 → 1024 → 512），或关掉浏览器/IDE。

### Q: 训练时出现 NaN，直接崩了
```
ValueError: The observation group 'policy' contains NaN values
```
**解法**：这个项目已经 patch 了 rsl_rl（NaN 就地清零 + 告警）。
如果又出现，说明物理发散太严重，检查：
- `reset_to_fallen` 的 z_range 是否太低（穿透地面）
- `effort_limit_sim` 是否太大
- `njmax`/`nconmax` 是否够

### Q: `--visualizer kit` 启动后进程被杀
**原因**：Isaac Sim RTX 渲染需要 >4 GB 显存，8 GB 卡不够。
**解法**：用 `--visualizer newton_gl`（轻量 OpenGL）。

### Q: kb_joy 报 `RCLError: failed to shutdown`，Z/X 没反应
这是 kb_joy 退出时的已知无害报错（Q 退出时 rclpy 被关了两次），**不影响 Z/X 功能**。

**Z/X 真正没反应的原因**：kb_joy 发布 `joy.axes[2]`，但消费它的是
`isaac/policy_node_isaac.py`（不是 sim_node）。如果策略节点没启动，
或者节点版本旧（height 观测格式不匹配），Z/X 就完全没效果。

**排查步骤**：
```bash
# 1. 确认 kb_joy 正常发 joy
ros2 topic echo /joy    # 按 Z/X，期望 axes[2] = -1.0 / +1.0
# 2. 确认策略节点收到 joy
ros2 topic info /joy    # 期望 Publisher count >= 2（kb_joy + policy_node）
# 3. 确认 /mujoco_action 有数据
ros2 topic hz /mujoco_action    # 期望 >= 50 Hz
```
如果第 1 步 axes[2] 没变化：kb_joy 版本旧，`colcon build --packages-select mjsim` 重编译。
如果第 3 步没数据：策略节点崩了，看它的终端报错。

### Q: `play_viewer.sh` 窗口打开但是黑的
**原因**：窗口还没完成初始化，或被其他窗口遮挡。
**解法**：等 2-3 分钟，用 `xdotool windowraise` 把窗口提到最前。

### Q: `play_viewer_kb.sh` 按键没反应
**排查顺序**：
1. Newton Viewer 窗口是否在前台？点一下窗口再按 `I`。
2. 终端有没有 `[kb] viewer 已绑定: NewtonViewerGL`？没有就还在初始化，等最多 3 分钟。
3. 遥测里 `cmd=(1.00,+0.00)` 变了吗？
   - 变了但 `vx` 不动 → **checkpoint 问题**（策略不会走），换
     `2026-11-06_18-15-41/model_2998.pt`，或先用 `eval_policy.py` 量化验证。
   - 没变 → 键盘轮询没接上，重跑并确认前台。

### Q: `ros2 run mjsim` 找不到包
**解法**：`source install/setup.bash`（每次开新终端都要）。

### Q: policy_node 报 `OBS_DIM mismatch`
**原因**：导出的策略是 36 维（旧），但节点期望 37 维。
**解法**：用最新的 `isaac/export_policy.py` 重新导出。

### Q: MuJoCo 里机器人侧翻后站不起来
**原因**：侧翻时轮轴垂直于地面（与重力夹角 cos=-1.0），轮子无法产生水平力。
**解法**：这是物理结构限制。起身训练用 `Isaac-Velocity-Flat-Nezha-GetUp`
（从倒地姿态开始），或者加"翻转"专用动作。
